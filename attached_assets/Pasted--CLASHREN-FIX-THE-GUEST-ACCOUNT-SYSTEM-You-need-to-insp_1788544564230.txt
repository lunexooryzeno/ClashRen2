# CLASHREN — FIX THE GUEST ACCOUNT SYSTEM

You need to inspect the existing ClashRen codebase first and then correct the Guest Account system.

**Do NOT rebuild the application from scratch.**
**Do NOT break existing authentication, navigation, matchmaking, wallet, profile, or other working functionality.**
Make the smallest safe changes necessary.

Use the existing ClashRen project architecture and preserve its current design system.

---

## 1. CORE RULE: GUEST IS EXPLORATION ONLY

A ClashRen Guest Account is NOT a normal player account.

A guest exists so that a new visitor can enter ClashRen immediately and explore the product before creating/signing into a real account.

The guest must be able to understand:

* What ClashRen is
* How matchmaking works
* What game modes exist
* What tournaments look like
* What the player experience looks like
* What rankings/history/features look like where appropriate
* How ClashRen's competitive ecosystem works

But the guest must NOT be treated as an eligible competitive player.

### Guest = Explore

### Registered Account = Compete

This distinction must exist throughout the frontend AND backend.

---

# 2. WHAT A GUEST CAN DO

A guest should be able to:

* Enter ClashRen without completing registration.
* Explore the Home screen.
* Browse available game modes.
* Browse tournament information.
* View public/preview matchmaking information.
* Explore the UI and major product flows.
* View demonstrations/previews of what happens during a match.
* Explore public rankings where appropriate.
* View example/limited content intended for discovery.
* Navigate around the product without being forced to register immediately.

The guest experience should feel like a real ClashRen session, not a broken or empty demo.

---

# 3. WHAT A GUEST CANNOT DO

A guest MUST NOT be able to:

* Enter a competitive matchmaking queue.
* Join a real match.
* Enter a paid match.
* Enter a free competitive match if the system treats it as an actual competitive match.
* Win rewards.
* Receive competitive rewards.
* Withdraw coins/money.
* Deposit money for competitive participation.
* Submit competitive match results.
* Submit financial claims.
* Create/modify a competitive Free Fire identity.
* Bind a Free Fire UID as a competitive identity.
* Participate in tournaments.
* Register for tournament slots.
* Create disputes for real matches.
* Claim competitive rewards.
* Access another player's private information.
* Perform any protected player operation.

Most importantly:

**Do not rely only on frontend buttons being disabled.**

The backend must reject unauthorized guest actions as well.

---

# 4. GUEST SESSION MODEL

Inspect the current authentication architecture.

Implement the guest as a temporary authenticated/session state if the existing architecture supports it.

For example, the system may conceptually distinguish:

```text
GUEST
REGISTERED_PLAYER
ADMIN
```

Do NOT blindly introduce a new database architecture if the existing project already has an appropriate session model.

The important requirement is that the backend can reliably determine:

```text
Is this request coming from a guest?
```

and enforce the appropriate permissions.

---

# 5. GUEST IDENTITY

A guest may receive a temporary session identifier.

Example:

```text
guest_session_id
```

But do NOT treat this as a permanent ClashRen player ID.

Do NOT give guests:

* permanent competitive user identity
* wallet ownership
* competitive reputation
* competitive trust score
* match statistics
* official ranking position
* permanent Free Fire identity

If guest data is stored, it should be clearly temporary and disposable.

# 8. IMPORTANT: FREE MATCHES

Do NOT assume:

> "It costs 0 coins, therefore guests can play."

That is incorrect.

If the match is a real competitive ClashRen match, it still requires a registered competitive identity.

Therefore:

```text
Guest → Cannot enter competitive match
Registered Player → Can enter if eligible
```

This applies even when:

```text
entry fee = 0
```

# 9. FREE FIRE IDENTITY

A guest must NOT be allowed to bind a Free Fire UID/IGN as their permanent competitive identity.

The correct flow is:

```text
Guest
 ↓
Create account / Sign in
 ↓
Player profile
 ↓
Bind Free Fire UID + IGN
 ↓
Eligibility checks
 ↓
Competitive matchmaking
```

Do not bypass this because the user started as a guest.

---

# 10. WALLET

Guests must not have a usable competitive wallet.

Do not give guests:

* real balance
* withdrawable balance
* deposits
* reward balance
* withdrawal functionality

If the UI shows coins to explain the product, make it clearly a preview/example rather than an actual spendable balance.

Never allow the frontend to manufacture a guest wallet balance.

---

# 11. REWARDS

Guest users cannot receive competitive rewards.

This includes:

* Match rewards
* Tournament rewards
* Winning rewards
* Daily competitive rewards where account eligibility is required
* Withdrawal rewards
* Promotional competitive credits

If ClashRen has public promotional information, the guest can VIEW the feature but cannot claim protected rewards until they have a registered account.

---

# 12. MATCHMAKING SECURITY

This is critical.

Do NOT implement guest restrictions only like:

```typescript
if (isGuest) {
  disableButton();
}
```

That is insufficient.

The backend endpoints responsible for competitive operations must verify authentication/authorization.

For example:

```text
POST /matchmaking/join
POST /matchmaking/leave
POST /matches/*
POST /wallet/*
POST /withdraw/*
POST /tournaments/*/register
POST /matches/*/dispute
```

must reject guest sessions where appropriate.

Use the project's existing authorization/error conventions.

Do not invent a completely new API style if existing middleware already handles this.

---

# 13. GUEST → REGISTERED CONVERSION

A major purpose of the guest mode is allowing users to explore first and then convert into a real account.

Therefore the transition should be smooth.

Example:

```text
Guest exploring
      ↓
Clicks "Play Now"
      ↓
Authentication gate
      ↓
Create account / Sign in
      ↓
Return user to the action they originally wanted
```

For example:

```text
Guest opens Lone Wolf
→ taps "Find Match"
→ authentication screen
→ creates account
→ returns to Lone Wolf
→ can now continue setup
```

Do not dump the user back to the homepage unnecessarily.

Preserve the intended destination where technically safe.


There must be no competitive activity attached to a guest that can later be converted into rewards.

Guest mode is exploration only.
