# ClashRen Instant Matchmaking, Automated Room Creation, Screenshot Verification, and Secure Prize Distribution Architecture

Build a complete esports tournament platform for **Free Fire** focused on ** instant matchmaking**, automated room creation through a dedicated host phone, screenshot-based winner verification through a secondary verification phone, a dispute system, wallet management, and a payout workflow that guarantees **a prize can only be distributed once under any circumstance**.

Focus on product architecture, workflows, state management, user experience, automation flow, verification flow, and payout safety.

---

# Core concept

The platform consists of five main components:

* **ClashRen Web App** (used by players)
* **Backend Server** (controls matchmaking, match states, wallet states, disputes, workers, and payouts)
* **Host Phone** (Android device running MacroDroid and Free Fire that creates rooms automatically)
* **Verification Phone** (separate Android device running MacroDroid that performs OCR and screenshot verification)
* **OCR and Image Verification Pipeline** running on the verification phone

The host phone is responsible only for **room creation**.

The verification phone is responsible only for **winner verification**.

Players do **not** need MacroDroid or a companion app.

The backend server is the **single authority** that controls matchmaking, room distribution, verification decisions, disputes, wallet updates, and prize distribution.

# Instant matchmaking flow

## Queue system

Players choose:

* Clash Squad 1v1
* Entry fee
* Region (if applicable)

When a player taps **Play Now**:

1. Verify that the player has sufficient coins.
2. **Deduct the entry fee immediately** from the player wallet.
3. Place the player into the matchmaking queue.
4. Continuously search for another compatible player.
5. The moment two players are available, create a match instantly.

The queue must remain active even while the host phone is busy creating another room.
1 match = 1 queue that mean in this example there are 2 players then the queue will be #1

Do not display queue numbers.

Instead display:

* Finding opponent
* Opponent found
* Waiting for room creation
* Estimated wait time
* One match ahead of you (if applicable)

# Host phone webhook architecture

The host phone is treated as a **Room Creation Worker**.

The backend server does not create rooms directly.

Instead, it sends a webhook request to the host phone one by one by the queue system.

Example:

`https://trigger.macrodroid.com/98315e1f-abce-4c9f-ab7d-87004928eb82/clashren?game_mode=89UBO&access_token=RANDOM_SECURE_HASH`

Where:

* `game_mode` is the room creation code
* `access_token` is a cryptographically random token generated for this specific room creation request

Example mapping:

* CS 1v1 Normal → **89UBO**

The game mode code determines exactly which MacroDroid room creation routine is executed.

---

# Access token workflow

For every room creation request:

1. Server generates a unique random access token.
2. Token is associated with:

   * Match ID
   * Worker phone ID
   * Request timestamp
   * Expiration time
3. Server sends webhook to the host phone.
4. Host phone performs room creation.
5. Host phone sends all responses back to the server using the **same access token**.
6. Server validates that:

   * Token exists
   * Token is not expired
   * Token belongs to that worker phone
   * Token has not already been completed

The token can be used only once per match.

This prevents duplicate room creation responses and replay attacks.

# Worker phone response protocol

The host phone continuously reports progress back to the server.

Each response includes:

* access_token
* phone_status
* msg_code
* response_code
* timestamp
* optional room data

Example statuses:

| phone_status        | msg_code            |
| ------------------- | ------------------- |
| Ready               | ready               |
| Launching Free Fire | launching_game      |
| Switching Guest ID  | switching_account   |
| Opening Custom Room | opening_room_menu   |
| Configuring Match   | configuring_room    |
| Creating Room       | creating_room       |
| Room Created        | room_created        |
| Sending Credentials | sending_credentials |

Example successful response:

* access_token
* phone_status = Room Created
* msg_code = room_created
* response_code = 200
* room_id
* room_password
* timestamp

The server receives these responses and updates the match state in real time.

# Winner submission architecture

Only the **winner** uploads a screenshot.

Requirements:

* Upload within **80 seconds**
* Screenshot must contain the Free Fire victory screen
* Screenshot must show the player nickname

## Temporary upload pipeline

The uploaded screenshot must **not be verified directly on the server**.

Workflow:

1. Winner uploads screenshot through ClashRen.
2. Server stores the screenshot in a **temporary storage location**.
3. Server generates a temporary file path or temporary file identifier.
4. Server sends a verification request to the **verification phone** containing:

   * Match ID
   * Player ID
   * Player nickname
   * Temporary screenshot path
   * Upload timestamp
5. Verification phone downloads the screenshot.
6. Verification phone performs OCR and image analysis locally.
7. Verification phone sends verification results back to the server.
8. Server immediately deletes the temporary screenshot unless a dispute is later opened.

The screenshot should remain temporary by default.

# Verification phone responsibilities

The verification phone is a dedicated OCR worker.

It must detect:

* BOOYAH
* VICTORY
* Winner screen layout
* Player nickname
* Screenshot quality
* OCR confidence score
* Template match confidence
* Resolution consistency
* Basic tampering indicators

The verification phone returns:

* VALID or INVALID
* Detected nickname
* Detected victory text
* OCR confidence
* Tampering suspicion score
* Verification timestamp
* Optional diagnostics

The server makes all decisions based only on this verification response.

---

# Verification decision

If verification is VALID:

* Mark VERIFYING_SCREENSHOT complete
* Mark winner as provisional winner
* Continue to provisional payout

If verification is INVALID:

* Reject submission
* Notify player
* Allow another upload only within the remaining submission window

# Dispute workflow

## No dispute within 10 minutes

* Unlock prize
* Finalize payout
* Mark match FINALIZED

## Dispute submitted

* Freeze pending prize
* Re-analyze winner evidence
* Analyze challenger evidence
* Compare OCR
* Compare timestamps
* Compare nicknames
* Compare match context

## If original winner was fake

* Reverse provisional payout
* Credit prize to actual winner
* Finalize match
* Suspend the fake claimant for **48 hours**

## If dispute was false

* Deduct **5 coins** from challenger
* Transfer 5 coins to falsely accused player
* Increase false dispute count
* Reduce challenger trust score

If the challenger has **0 coins**:

* Suspend challenger for **12 hours**
* Notify the opponent that a false dispute penalty was applied

# Prize distribution safety (critical requirement)

The system must guarantee that **a prize can never be distributed twice**.

This is mandatory.

## Single payout authority

Only the backend server can authorize wallet credits.

The host phone and verification phone can never credit wallets directly.

## Prize states

Every prize must exist in exactly one state:

NOT_CREATED

PENDING

LOCKED

FINALIZED

REVERSED

Once FINALIZED, the prize can never return to any previous state.

## Idempotent payout

Each match must have one unique payout identifier.

If payout is triggered multiple times because of:

* retries
* duplicate requests
* browser refresh
* network reconnect
* server restart
* background jobs
* verification retries
* dispute retries
* admin retries

the server must recognize that the payout already exists and refuse any duplicate distribution.

## Duplicate protection

The server must reject:

* repeated payout requests
* repeated dispute resolutions
* repeated screenshot approvals
* repeated admin actions
* repeated background jobs

## Finalization lock

After finalization:

* dispute window permanently closes
* prize unlock completes
* withdrawal becomes available
* all payout actions become permanently read-only

A finalized prize can never be credited again.

This guarantee must survive crashes, reconnects, duplicate events, and repeated verification responses.

# Security guarantees

The architecture must ensure:

* webhook URLs are admin-managed
* access tokens are single-use
* worker responses are authenticated
* duplicate responses are ignored
* room credentials are distributed only by the server
* players can view opponent details before joining
* sharing room credentials can lead to suspension
* worker phones cannot directly modify wallets or payouts
* screenshots are stored only temporarily
* prize distribution can occur only once
* every critical action is controlled by the backend server

This architecture provides instant matchmaking, automated room creation, screenshot verification through a secondary worker phone, dispute-based fraud protection, secure wallet management, and a payout system that guarantees **one-time prize distribution** while remaining scalable for future expansion.
